# Skill Evolution Engine (SEE) — Self-Evolving Skills Architecture

Status: implemented (validated end-to-end 2026-08-08)
Author: Halldrix + Hermes
Supersedes: N/A (new subsystem)
Location: `agent/skill_evolution*.py` (5 modules)
Tests: `tests/agent/test_see_*.py` (36 tests)

## Context

Hermes Agent ships skills (`SKILL.md` files) that are consumed at runtime by AI agents. When a skill fails — because it misses a dependency check, assumes an installed CLI, lacks a fallback path — the failure is diagnosed and fixed **manually**: an engineer reviews the transcript, finds the missing step, and patches the SKILL.md by hand.

The cost of this loop is human attention. Failures repeat across profiles, environments, and skill versions. We wanted a subsystem that could:

1. **Diagnose** why a skill failed (generate falsifiable hypotheses about the defect)
2. **Prove** the diagnosis (generate an executable test for each hypothesis)
3. **Fix** the skill (generate candidate patches to SKILL.md)
4. **Choose** the best fix with evidence, not vibes (an evidence matrix over the patch tree)
5. **Stay cheap** (budget tracking, test caching, free-tier model defaults)

## Decision

Build a self-contained **Skill Evolution Engine (SEE)** as five independent modules under `agent/`, driven by a PUCT tree-search loop that delegates the four cognitive roles (hypothesis, test, patch, execute) to real LLM sub-agents.

Evidence-based patch selection: never merge a patch because it *looks* right; merge it because its node in the evidence matrix has the highest fraction of passing tests.

## Key Architecture Choices

### 1. PUCT search tree, not a single-shot fix

| | Single-shot "ask LLM to fix skill" | PUCT tree (chosen) |
|---|---|---|
| Explores multiple patch candidates | No — one answer | Yes — K candidates per node |
| Backtracks when a patch fails | No | Yes, via UCB1 selection |
| Evidence backlog | None | Matrix of test results per node |
| Cost | Cheaper (fewer calls) | ~8–12 min (PUCT loop) |

Worth it: the *best patch* alone was always the one a human would have written; single-shot fixes missed dependencies because the LLM never tested them.

### 2. Per-role LLM delegates (not one big prompt)

SEE spawns a dedicated, isolated `AIAgent` per cognitive role, each with:
- `ephemeral_system_prompt` (role instructions)
- `enabled_toolsets=[]` — the reflection agent only *reasons*
- `skip_memory=True / skip_background_review=True` — no context leakage
- `quiet_mode=True` + `log_prefix=[see-<role>]`

Model routing per role (`evolution.models.<role>`) with fallback chain: role-specific → `delegation.*` → parent `AIAgent`. Roles are asymmetric:
- `test` is the **expensive, critical** role (needs a capable model)
- `execute` is cheap — the output is what gets tested

### 3. Sandboxed test execution

Generated tests are pure functions (`check(output, files) -> dict`) executed in a restricted namespace with only `json/re/os.path/yaml/io` available. Validated twice:
- **Static**: syntax check, forbidden-token scan (`subprocess/socket/urllib/requests/open()` blocked), `def check(output, files)` signature
- **Dynamic** (`validate_test_strict`): dry-run against 3 adversarial scenarios to catch trivially-permissive always-true tests

This is a sandbox, not a security boundary — tests come from a user-configured LLM, not hostile code.

### 4. Test cache (reads/writes are expensive)

Test code is generated by the most expensive model per domain. `TestCache` persists them per-skill at
`~/.hermes/skills/<category>/<skill>/.evolution_cache/` with:
- hash key = `(hypothesis_description, skill_hash, observable_behavior)`
- advisory `fcntl.flock`, best-effort (any I/O failure degrades to miss)
- stale-marking on skill change, TTL pruning (30 days), audit archive for refuted tests

### 5. Budget tracker with predictive cost caps

`BudgetTracker` enforces `max_cost_usd` using per-role default token budgets + a pricing table.
`check_budget()` before each spawn raises `BudgetExceededError` if `spent + predicted > cap`.
Warnings at 80% of budget. Unknown models default to $0.00 — making the free-tier validation runs possible.

## In-Scope / Out-of-Scope

- In: hypothesis, test generation/validation, patch generation, simulation, evidence matrix, best-node selection, budget, cache
- Out (deferred): model fallback chains *inside* a role, `decide` role (currently deterministic `best_node_id`), PR auto-generation, deployment to upstream

## Alternatives Considered

### A. Rule-based skill linter
- Pros: deterministic, no LLM cost
- Cons: cannot discover novel defect classes; evades any check the linter doesn't know. Rejected.

### B. Single-shot "fix this skill" prompt
- Pros: cheapest, fewest calls
- Cons: no verification, no evidence matrix, cannot reason about truth (LLM fixes often invent code that doesn't apply). Rejected — validation session showed single-shot patches skipped the dependency check entirely.

### C. Agent-simulation (run the skill against the task, check stderr)
- Pros: closest to production
- Cons: cannot run arbitrary commands from the safety sandbox (writes, network). Rejected as the *only* mechanism; kept `delegate_execute` as the cheap simulation role.

### D. hypothesis-first, test-first ordering
- Both orders were prototyped; the `hypothesis → test → patch → simulate` loop (chosen) front-loads the diagnosis so patches are targeted against falsifiable claims. Test-first tends to over-fit to the one observed failure.

## Consequences

**Positive:**
- Skills self-heal without manual review (validated on 2 real skill failures, both producing the exact fix a human wrote)
- Evidence over vibes: no patch merges without a passing test
- Cheap validation: free-tier models, $0.00 total cost in E2E runs
- Isolation: per-role delegates cannot leak parent context

**Negative / costs:**
- ~8–13 min per evolution run (LLM-dominated); 15+ LLM calls per run
- Material: budget caps still required for real deployments (paid models)
- Test cache invalidation is skill-hash-bound, so a skill that changes often re-generates tests
- No confidence interval on hypotheses — "confirmed" today means "all tests pass at one node"
